## 多 GPU 部署与加速、占地约束、进度条（未发布）

### 两万面镜的时间花在哪里

年度价值逐工况求 APS。大镜场（20 m² 定日镜、Ø14 m × 16 m 吸热器、塔高 200 m，`scripts/gpu_benchmark.py --plant large`）一个工况单核实测：

| 镜数 | 每个工况（单核，编译内核） | 光斑核（响应、复核、热流图、联合姿态上界） | 均匀度局部搜索 | 贪心 | 阴影遮挡 | 截获率积分 |
| --- | --- | --- | --- | --- | --- | --- |
| 4,880 | 20.9 s | 46% | 25% | 9% | 5% | 7% |
| 19,622 | 111.6 s | 46% | 30% | 8% | 6% | 5% |

两万面镜时一个工况近 2 分钟，一套布局的晴空年度有 223 个工况。加速分三层：

1. **能并行的都放到 GPU**：光斑核及其归约、截获率积分、阴影遮挡的光线求交，以及**均匀度局部搜索**。局部搜索是坐标搜索，镜子必须一面接一面地换瞄准点，但每一步要给 K + 1 个候选行、每行几百个网格打分：一个工况用一个线程块，各 warp 分管候选行、各线程分管网格，一步只需几次同步（`gpu_search.py`）。
2. **串行部分在 CPU 上编译运行**（Numba）：均匀度局部搜索和贪心 APS，与原 numpy 代码**逐位相同**。没有显卡、或 GPU 内核出错时自动用它们。
3. **工况级多进程铺满所有核心和显卡**：每个工作进程分到一张卡，并把自己的 BLAS 线程限制在分到的核心数内。

### 第一轮实测反馈与这次的改动

在 8 × RTX 2080 Ti 上的第一轮实测：单进程 GPU 比 CPU 快 1.8–2.1 倍，但 23 个工作进程时 GPU 每分钟 54.6 个工况，反而低于 CPU 的 67.4 个；各卡平均利用率只有 4–5%。原因有两个：

- **线程超额订阅。** 每个工作进程的 numpy/OpenBLAS 都按整机核数开线程，23 个进程就是几百个线程抢 24 个核，单进程却看不出来。现在每个工作进程只开它分到的那份（`parallel.worker_threads`，`CSPAPS_WORKER_THREADS` 可改）。4 核机器上 4 个进程：每分钟 9.5 → **24.5** 个工况（2.6 倍），单进程速度不变。
- **GPU 上的活太少。** 1,600 面镜时光斑核只占一个工况的一半，另一半是 CPU 上的串行搜索，显卡大部分时间在等。现在局部搜索、阴影遮挡也在 GPU 上，贪心在 CPU 上编译运行。

### 在多卡机器上运行

```bash
pip install -e ".[gpu]"                          # CuPy（CUDA 12 驱动；CUDA 11 驱动改装 cupy-cuda11x）
nvidia-cuda-mps-control -d                       # 建议：每张卡多个进程时让它们的核函数同时执行
CSPAPS_GPU=1 python -m cspaps.backend            # 逐卡对比 GPU 与 CPU 的结果和速度
python scripts/gpu_benchmark.py cases/aksai_demo.yaml --plant large --heliostats 5000 20000 --scenarios 2 --throughput 48 --workers -1 --gpus 8
cspaps optimize-layout cases/aksai_demo.yaml --mode deep --gpus 8 --workers -1     # 正式计算
```

- **用哪几张卡由用户指定**：
  - **界面**：左侧栏当前算例下方的“⚡ 计算资源”框。“计算设备”选 **GPU 加速** 或 **仅 CPU**；“使用哪些显卡”勾选具体的卡（上方列出检测到的型号和显存）；“并行进程数”设同时求解的工况数。框底写明“将使用：GPU 0、1、2（3 张）+ CPU 23 个进程”，每个“开始计算”按钮上方和运行中的进度条下方也显示这一行。没检测到显卡时，框里写明原因（没装 CuPy、驱动不可用或没有显卡）和解决办法。
  - **启动界面时**：`cspaps gui --gpus 0,1,2,3 --workers 23`（Windows：`Start-CSP-APS.cmd --gpus 0,1`），进入界面后仍可在侧栏改。
  - **命令行计算**：每个算例命令都有 `--gpus 4`（前 4 张）、`--gpus 0,2,5`（指定编号）、`--gpus 0`（只用 CPU）、`--gpus all`；也可设环境变量 `CSPAPS_GPUS=4` 或 `CSPAPS_GPU_DEVICES=0,2,5`。
- **CPU 数从系统读取**：按进程亲和性（taskset、集群调度器分到的核）和容器 CPU 配额取可用核数，不是整机核数。进程数按 CPU 核数取，不按显卡数取。
- **不把电脑占满**：默认留约 15% 的 CPU 给系统和其他程序（24 核留 4 个，即 20 个工作进程；`CSPAPS_RESERVE_CPUS` 或界面“给系统留几个 CPU”可改）。计算深度三档和 `--workers -1` 都按留出余量后的核数取；手动填更多进程时界面会提醒。工作进程以较低优先级运行（Linux nice +10，Windows“低于正常”），鼠标、浏览器和桌面不会被卡住。每次启动进程池时还按可用内存限制进程数：每个进程按 1.5 GB 估计（`CSPAPS_WORKER_MEM_GB`，两万面镜可调大），始终留出 max(2 GB, 15%) 内存，避免换页卡死。每张显卡留出 15% 显存给显示和其他程序。
- **分卡**：工作进程按顺序轮流分到选定的卡上；同一张卡上的进程平分显存（CuPy 内存池上限与分块大小自动调整）。
- **长时间运行的核函数**：GPU 局部搜索一个工况的核函数要运行数秒。专门计算用的 Linux 显卡没有问题；如果某张卡同时驱动桌面（Windows 或带看门狗的 X 桌面），可能被看门狗中断，这时不要选这张卡，或设 `CSPAPS_GPU_SEARCH=0` 把局部搜索留在 CPU。
- **显存**：2080 Ti（11 GB）、3080（10 GB）都够用。两万面镜一个工况的光斑响应约 1 GB（float32），每张卡同时 3–4 个进程没有问题。

| 环境变量 | 默认 | 作用 |
| --- | --- | --- |
| `CSPAPS_GPU` | 关 | `1` 打开 GPU 后端（需要 CuPy 和显卡，找不到时自动回到 CPU） |
| `CSPAPS_GPUS` | 全部 | 用前几张卡；`0` = 只用 CPU |
| `CSPAPS_GPU_DEVICES` | 全部 | 参与计算的卡，逗号分隔（优先于 `CSPAPS_GPUS`） |
| `CSPAPS_GPU_SEARCH` | 开 | `0` 把均匀度局部搜索留在 CPU（光斑核仍在 GPU） |
| `CSPAPS_GPU_MIN` | 2,000,000 | 低于这个元素数的整块光斑矩阵留在 CPU；只传回归约结果的计算从它的 1/8 起上 GPU |
| `CSPAPS_GPU_BLOCK` | 8,000,000 | 显卡上一块的元素数上限 |
| `CSPAPS_WORKER_THREADS` | 留出余量后的核数 ÷ 进程数 | 每个工作进程的 BLAS / OpenMP 线程数 |
| `CSPAPS_RESERVE_CPUS` | 约 15% | 留给系统的 CPU 数 |
| `CSPAPS_WORKER_NICE` | 10 | 工作进程降低的优先级（0 = 不降） |
| `CSPAPS_WORKER_MEM_GB` | 1.5 | 每个工作进程的内存估计，用于按可用内存限制进程数 |
| `CSPAPS_JIT` | 开 | `0` 关闭编译内核，回到 numpy 代码（结果相同，只是慢） |

**精度与可比性。** CPU 编译内核（局部搜索、贪心）与 numpy 逐位相同：复现了 numpy 的求和顺序，运行时先对照本机 numpy 检验，不一致就自动用 numpy。GPU 结果与 CPU 相差在舍入以内：GPU 局部搜索的移动规则、顺序和每个网格的通量与 CPU 完全一样，只是行求和的相加顺序不同。同一台机器、同一型号显卡上重复计算逐位相同；年度价值会记录后端和显卡型号（`backend`、`gpu_model`），比较布局时不要混用 CPU 与 GPU、或不同型号显卡算出的结果。

> 开发环境没有显卡。GPU 局部搜索的核函数源码同时能按 C++ 编译：测试在 CPU 上逐线程执行同一份代码，与 CPU 内核比较（移动完全相同，每个网格的通量逐位相同）；其余 GPU 路径用严格的 CuPy 替身（`tests/fake_cupy.py`）对照 CPU 结果测试。真正的 CUDA 编译在显卡机器上进行，失败时打印一次警告 `GPU local search unavailable` 并自动改用 CPU 内核。部署后请先运行 `python -m cspaps.backend` 和 `scripts/gpu_benchmark.py`，确认没有这条警告、每张卡与 CPU 一致，再用于正式计算。

### 现场数据试用的反馈（阿克塞 2026，11,960 面镜）

- **载入算例不丢文件**：算例 YAML 里的相对路径（镜场坐标、气象文件等）按 YAML 所在的文件夹查找。以前单独上传 YAML 时，这些文件没有一起上传，就会报“无法生成镜场”。现在左侧“📂 载入算例”有三种方式：从本机已有的算例里选，或输入算例 YAML（或所在文件夹）的完整路径直接打开；上传时把 YAML 和它引用的 CSV 一起选中；或把整个算例文件夹压缩成 ZIP 上传。如果引用的文件仍然找不到，页面顶部会列出缺哪些文件、应该放在哪里，可以直接补传。
- **“用当前算例开始”**：首页的任务卡片在载入了自己的算例时，第一个按钮是“▶ 用当前算例开始：算例名”，直接带着当前算例进入工作区。演示算例改为单独的“改用演示算例试算”，会替换当前算例。
- **“演示数据”标记跟着算例走**：每次载入算例都会重新判断来源，只有内置演示算例才显示“演示数据”。首页的数据说明写的是当前算例实际用的镜场文件和气象文件。
- **功率–均匀度权衡曲线带吸热器热流分布**：每个 λ 的方案都在吸热器展开图上画出入射热流（各 λ 并排、同一色标），选中一个 λ 看大图：管屏编号、管屏分界、接近上限（90% / 100%）的等值线、细网格复核热点；旁边是各管屏峰值热流对允许热流、各管屏吸收功率；下面是所有 λ 的周向与高度分布曲线。数据另存为 `pareto_flux.npz` 和 `pareto_panels.csv`。
- **色标不再夸大或掩盖差别**：
  - 多个 λ 对比时，热流图旁边有“色标”选项：**统一色标 0 – 最大**（真实大小）；**统一色标·增强对比**（从受光区低值拉到最大值，仍是一个色标）；**与参照 λ 的差值**（红 = 变热、蓝 = 变冷，所有 λ 用同一个对称色标：差别大颜色深、差别小颜色浅，色标数字就是真实的 kW/m²）。
  - DNI 色标至少跨 100 W/m²。全场 DNI 只差零点几 W/m² 时，不会再被拉满整个色标显得“差别很大”。色标下方注明实际范围（例如“实际 71.00–71.49”）。
- **瞄准结果的热流图是全部镜子叠加的**：瞄准优化结果“吸热器热流与瞄准点”一页最上面是“全场叠加热流：全部 N 面工作镜”——吸热器展开图上每个格子的热流都是所有工作镜的光斑在那里叠加的结果，图上不画瞄准点，专门用来看整体是否均匀；旁边是各管屏峰值热流对允许热流、各管屏吸收功率，下面是周向与高度分布，标题下列出吸收功率、平均热流、评价网格峰值、细网格复核峰值和二维 / 周向 / 高度 CV。下面的“瞄准点与光斑”图底色仍是全场叠加热流，只是在上面画出抽样的瞄准点和光斑圈（圈只画一部分镜子，以免盖住热流）。
- **时刻必须落在气象文件范围内**：以前选的时刻不在气象文件里时，程序悄悄取最近的一条记录（例如 2025 年的时刻取到 2026 年文件第一条的 71 W/m²），热流图因此又暗又碎。现在时刻选择框下方写明气象文件覆盖的时段（例如“2026-06-17 08:30 – 2026-06-21 07:30，96 条，间隔 60 min”），默认时刻落在文件内（算例的时刻不在文件内时取文件里 DNI 最大的一条）；选到文件之外会报错并停用开始按钮，命令行同样报错，不再静默取值。容许偏差为 max(1 h, 1.5 × 记录间隔)。
- **最优性证书不再把内存占满**：证书模型（上界与松弛取整）按 每个非零项 48 字节 估计内存。11,960 面镜、21 个候选点、10,260 个网格约需 38 GB，以前会把电脑内存占满后被系统杀掉。现在超过“可用内存 − max(2 GB, 15%)”时跳过证书，结果页说明需要多少、可用多少，以及怎样缩小（减少候选瞄准点或求解网格）；方案本身仍按全部镜子的光束在细网格上复核热流上限。年度正式值不看本机内存，只按固定的 8 GB 模型规模决定是否算证书，保证不同机器结果一致；通量价格换位遇到放不下的模型时改用能量定价。

### 占地约束：土地权重 κ

布局多占一公顷地，就要多贡献足够的年度热价值才值得选。布局目标改为

J(L) = E_abs(L) − λ_L·Π(L) − κ·A(L)

- **A(L)**：全部镜心地面坐标的凸包面积，单位公顷。对一套固定镜位只算一次，在年度求和之外。
- **κ**：单位 MWhₜₕ／（公顷·年）。κ = 100 表示每年最多愿意牺牲 100 MWhₜₕ 的等效热价值来省一公顷地。默认 0（不计占地，排名与以前完全相同）。
- **布局搜索和最终排名都用 J**：差分进化与贝叶斯搜索的目标、镜位微调、正式换位的接受条件、最终排名。固定镜位下的逐时瞄准仍用原目标。
- **硬约束 A(L) ≤ A_max**（`layout_opt.max_land_ha`）：工程上只给这么多地时直接设上限，在上限内最大化原年度得分，不必猜土地价格。超出上限的布局不参与排名，搜索中也排在所有满足上限的布局之后。

**κ 怎么定。** 软件会给推荐值：

1. 有土地报价时：κ = 每公顷年化土地成本 ÷ 每 MWhₜₕ 有用热量的边际价值（参数 `land_cost_per_ha_year`、`heat_value_per_mwh`，同一货币；一次性征地费先折算成年成本）。
2. 没有价格时：κ = 0.05 × 参考布局每公顷的年吸热量，即多占 10% 的地，至少要多带来 0.5% 的年吸热量。
3. 布局比较结果里列出**排名切换点**：每套更省地、但 κ = 0 时得分较低的布局，在 κ 超过多少时会排到第一。例如阿克塞 473 面镜、12 个代表工况的一次结果：自由镜位 3 比初始布局多占 1.831 公顷、年度得分多 280.1 MWhₜₕ，切换点 κ ≈ 153；低于 153 时自由镜位 3 排第一，高于 153 时更紧凑的初始布局排第一。

界面的布局比较结果里有 κ 滑块（不重新求解瞄准方案，直接重新计分）、占地与土地扣分两列、推荐值和“把 κ 写入参数”按钮。命令行：`cspaps optimize-layout … --land-weight 150 --max-land-ha 16`；对已保存的结果换 κ 重新排名：`cspaps rescore <结果目录> --lambda-layout 0.3 --land-weight 150`。

## 0.9.0 晴空年度设计基线 + 年度计算加速

### 布局设计基线改为“晴空年度”

以前的年度工况来自实测气象年，还叠加了人为的“东亮西暗”、移动云影等空间 DNI 地图，这些都是极端测试条件，不适合直接决定镜子放在哪里。现在布局评分只比较镜位本身的全年光学表现：哪一侧多放镜子，由本站全年太阳轨迹、镜间遮挡和吸热器受热均匀性决定。

1. **全年取 20 个代表日**（`scenarios.n_days`）。全年按日期等分成 20 段，每段取中间一天，权重 = 该段天数（合计 365 或 366 天），覆盖各季节的太阳赤纬和日照时长。每个代表日保留从早到晚的全部工作小时：太阳高度角 ≥ `annual.min_sun_elevation_deg`（默认 5°）且 DNI ≥ `annual.min_dni_w_m2`（默认 0）。冬季早晨太阳低，只要达到门槛也参与评价。
2. **每小时一个全场共享的晴空 DNI**（`scenarios.clear_sky_model: ineichen`）。Ineichen–Perez 晴空模型：按日期的地外辐照、站址海拔和当地典型林克浑浊度（pvlib 的站址月气候值，按日插值；有当地实测时可填一个数或 12 个月值，`scenarios.linke_turbidity`）。早晨、正午、下午各有自己的 DNI。同一小时内每面镜的余弦、塔影、镜间阴影与遮挡、截获仍按各自位置计算。
3. **每套布局逐小时重新求 APS**。每小时满足热流上限，计算吸收功率和当时的均匀性惩罚，乘“代表天数 × 1 h”累加。所有候选布局使用完全相同的日期、时段和权重（工况集指纹相同才允许比较）。

结果明确标为 **晴空年度吸热量**（E = Σ h·P）和 **晴空年度综合得分**（V = Σ h·(P − λ_L U)），界面、导出和命令行都用这两个名字。阿克塞 2024 年：20 个代表日共 223 个工作小时工况，代表 4,080 个全年工作小时，DNI 能量与全年逐时晴空相差 0.002%。

**20 个代表日够不够？** 阿克塞初始镜场最靠近塔的 100 面镜，对全年 4,080 个工作小时逐时求 APS 作为真值（晴空年度综合得分 14,033.3 MWhₜₕ）：10 / 20 / 40 个代表日的误差为 −0.09% / +0.01% / −0.06%，控制变量修正后为 +0.01% / −0.00% / +0.01%。晴空口径下 20 个代表日已足够，控制变量只作为核对另列。复现：`python scripts/validate_annual_estimators.py --clear-sky`（4 核约 1 小时）。

人为的空间 DNI 地图、移动云影、实测云量和极端天气都不进入布局评分。它们仍然可用，但只作敏感性分析（`scenarios.source: weather`，界面标为“站址气象年 + 空间 DNI（敏感性分析）”）。0.5–0.6 的三站址研究就是这种敏感性分析，`scripts/site_studies.py` 仍按原口径复现。三个站址算例和演示算例的默认口径都已改为晴空代表日。

> 注意这里的取舍：直接读气象站实测逐时 DNI，即使全场取同一个值，云造成的辐照下降也已经在数据里。晴空口径回答的是“在同一套常规日照条件下，把这批镜子建在哪里，全年能吸收更多热量、受热更均匀”，不是“这一年实际能发多少电”。

### 年度计算加速

年度价值 V(L) = Σ_s h_s (P_s − λ_L U_s) 的定义不变，改的是怎样算它、怎样用它找布局。五项改进都可单独开关，推导见[模型说明 0.9 节](docs/MODEL.md)。下表注明每个实测用的是哪种工况集（晴空基线之前的实测用气象年工况）。

| 改进 | 默认 | 收益（实测，阿克塞） | 代价 |
| --- | --- | --- | --- |
| ① 控制变量修正年度值 | 开（另报 V_cv，排名仍按 V） | 100 面镜、均匀 DNI，对逐时 APS 真值：K = 6 / 12 / 20 / 40 个工况时 V 偏高 2.25% / 1.21% / 0.59% / 0.40%，V_cv 误差 +0.03% / +0.02% / −0.03% / −0.02%（气象年、全场均匀 DNI）；晴空代表日本身已在 0.1% 以内（见上） | 一次全年逐时中心瞄准（不解 APS） |
| ② 复用：同方向共用光斑响应、DNI 齐次复用、共用太阳方向 | 共用响应（结果逐位不变） | 气象年 12–20 个工况：同方向共用响应省 10–17% 时间；再加热启动又省约 11%，V 变化 +0.04%。晴空代表日每个小时方向不同，主要靠热启动和多布局共用进程池 | 无 |
| ③ 分级保真的贝叶斯布局搜索 | 关（`search_method: bayes`） | 473 面镜、每种方法 10 分钟、2 个种子（气象年 12 个工况）：差分进化 V 29,393 / 留出 29,050 MWhₜₕ，贝叶斯 29,358 / 29,023，低约 0.1%。4 核下差分进化评价了约 536 个布局，贝叶斯约 20 个；默认仍用差分进化 | 每个布局少量工况的 APS |
| ④ 通量价格指导换位 | 开（`swap_pricing: dual`） | 一轮换位（初始镜场最靠近塔的 80 / 150 面）：气象年 8 个工况，能量定价 +6.9 / +8.5 MWhₜₕ，通量价格 +30.9 / +28.2；晴空 20 个代表日（223 个小时），能量定价 +37.6 / +65.0，通量价格 +51.8 / +66.7。四次都不差于能量定价，优势从 3% 到 4 倍不等 | 每轮约多一个布局的计算 |
| ⑤ 多核与 GPU | 多布局共用进程池；GPU 需 `CSPAPS_GPU=1` | 多个布局的所有工况一起分到全部核心；GPU 见下 | 无 |

**① 为什么能这么准。** 代表工况的误差主要来自“代表状态不等于它所代表的那些小时的平均”。中心瞄准年能量与 APS 年能量高度相关，而逐时算中心瞄准很便宜。对每个工况，用它的全部成员小时的中心瞄准能量除以代表状态的中心瞄准能量，得到修正系数，乘到这个工况的 APS 结果上。6 个工况加修正，比 40 个工况不加修正更准。复核脚本：`python scripts/validate_annual_estimators.py`（逐时 APS 参考值，4 核约 1 小时）。默认排名仍按正式 V（需求口径、逐位可复算）；`layout_opt.rank_by: value_cv` 改按修正后的全年估计排名。

**④ 通量价格是什么。** 每个工况的 APS 上界在计算中会给吸热器每个网格一个“拥挤价格”（通量限值的拉格朗日乘子）。一个空闲镜位值多少 = 它自己能送上去的功率 − 价格 × 它会加在各网格上的热流，取最好的瞄准点；一面镜子的代价 = 去掉它损失多少 P − λU。按“价值 − 代价”配对换位，重新逐工况求解后 V 提高才接受。原来的能量定价只看中心瞄准年能量，看不到哪里已经顶到限值。单独加入一个镜位的增益不会超过它的价格加上界差额，这一点已对穷举最优验证。

**⑤ 在 GPU 机器上。** 光斑响应、细网格复核和热流图都经过同一个光斑核。装好 CuPy 后打开：

```bash
pip install -e ".[gpu]"                 # CuPy for CUDA 12.x
CSPAPS_GPU=1 python -m cspaps.backend    # GPU 与 CPU 结果对比和加速比
CSPAPS_GPU=1 CSPAPS_GPU_DEVICES=0,1,2,3,4,5,6,7 cspaps optimize-layout cases/aksai_demo.yaml --mode deep
```

多卡分配、显存分摊和各项设置见上面的“多 GPU 部署与加速”（工作进程按顺序轮流分到 `CSPAPS_GPU_DEVICES` 的各张卡）。打开 GPU 后进程池改用 `forkserver`（CUDA 不能在复制出来的子进程里继续用），自己写的脚本需要 `if __name__ == "__main__":` 保护。GPU 结果与 CPU 相差在 float32 舍入以内，不逐位相同，所以年度价值会记录所用后端，比较布局时不要混用两种后端。没有 CuPy 或显卡时自动回到 CPU，结果与以前逐位相同。

新选项都在布局页的高级设置里，带“快在哪里、深在哪里”的说明。复现本节数字：`python scripts/acceleration_studies.py`（换位、复用、DE 与贝叶斯对比）。

## 0.8.0 算法怎么选：快速 / 标准 / 深度思考

三个任务（单时刻瞄准、比较已有布局、搜索新布局）都有三档“计算深度”。软件按镜数和这台计算机的实测速度估计每档要算多久，推荐时间预算内最深的一档。界面上默认是“当前设置（不改动）”，用户选中某一档才写入对应设置，之后仍可在高级设置里逐项修改。

| 档位 | 什么时候用 | 单时刻瞄准算什么 | 年度比较 / 布局搜索算什么 |
| --- | --- | --- | --- |
| ⚡ 快速 | 先看结果、调参数 | 贪心 APS 一次求解 + 细网格通量复核，不算最优性差距 | 比较：12 个工况、每工况 1 次联合姿态试探；搜索：初筛 2 代，前 1 名在 6 个工况上正式排名 |
| ◎ 标准 | 日常使用 | 再按镜子真实姿态复核镜间遮挡（联合姿态），松弛取整 4 轮，给出差距 | 比较：20 个工况、2 次试探，对得分最接近的工况补算；搜索：初筛 4 代，前 2 名 12 个工况，通量价格换位 1 轮 |
| ◆ 深度思考 | 定方案、定稿前 | 候选瞄准点加密一倍（嵌套加密，标准档的候选都保留），松弛取整 16 轮，上界迭代更久 | 比较：40 个工况、4 次试探、每工况松弛取整，60 个工况核对采样误差；搜索：初筛 16 代、前 5 名 20 个工况，通量价格换位 3 轮、镜位微调 8 次，独立云图复核 |

0.9.0 起布局评分的默认口径是晴空代表日（每档都逐时计算全部代表日，深度思考另用加倍的代表日复核）；表中的工况数只对气象年口径（敏感性分析）生效。

**规模分档**（按镜数；能否放进时间预算由时间模型决定）：

| 档 | 镜数 | 说明 |
| --- | --- | --- |
| 验证级 | 姿态组合 ≤ 256（约 5 面以内） | 穷举全部组合，得到含镜间遮挡的候选集全局最优 |
| 小规模 | ≤ 1,000 | 单个工况几秒，预算宽松时直接用深度思考 |
| 中等规模 | 1,000–5,000 | 单个工况十几秒到半分钟，年度任务的档位差别明显 |
| 大规模 | > 5,000 | 单个工况分钟级。这时贪心解离上界只差约 0.001%，深度思考不做松弛取整，时间改投更多工况、更密的候选点和更多联合姿态复核 |

**时间从哪里来。** 每一档的耗时按 t = a·N^p 估计，N 为镜数，指数 p 限制在 1–1.3。镜子越远光斑越大、遮挡邻居越多，所以单面镜的成本随规模缓慢增长。内置系数在一台 4 核机器上实测（427 / 1,049 面镜）。在你的机器上运行下面的命令，会在约 10 分钟内实测并写入 `~/.cspaps/calibration.json`，之后界面和命令行都按本机数值估计：

```bash
cspaps calibrate cases/aksai_demo.yaml --sizes 400 1200 2400
```

年度任务按“工况数 × 单工况耗时 ÷ 并行进程数”估计。现在界面里的后台任务也会使用多进程：能序列化的计算用全部核心减一，遇到 Windows 热重载等无法序列化的情况自动退回线程。GPU 见 0.9.0。

```bash
cspaps advise cases/aksai_demo.yaml --task compare --budget-min 30            # 三档的含义、预计时间和推荐
cspaps advise cases/aksai_demo.yaml --task search --budget-min 60 --heliostats 15000   # 假如镜场扩大到 1.5 万面
cspaps layout-value cases/aksai_demo.yaml --layouts initial a.csv --mode deep  # 按某一档直接计算
cspaps aps cases/aksai_demo.yaml --time "2024-03-19 15:00" --mode fast
cspaps optimize-layout cases/aksai_demo.yaml --mode standard
```

## 0.7.2 塔影、光斑大小与 Windows

**塔影按塔高计算。** 塔影由两段圆柱遮挡：

- 塔身：塔身直径，从地面到塔顶，塔顶高度取 `receiver.tower_height`；
- 吸热器：吸热器直径，从吸热器底到顶。

塔高不填时取吸热器底部，镜面高度取镜场坐标 z（默认 `heliostat.pivot_height`），没有写死的高度。平面图上的塔影画在镜子所在的高度，图例写出塔高、吸热器顶和镜轴高度。

**瞄准点图显示光斑大小。** 吸热器二维展开图上：

- 点越大，光斑越大；
- 悬停可看光束截面上的 σ、光斑在吸热面上的 2σ 宽和高、入射角和截获比例；
- 点图例“光斑轮廓”可按真实尺寸画出每个光斑的 2σ 椭圆。

**Windows。** 中文 Excel 另存的 GBK 编码 CSV 可直接导入；同一工况集在 Windows 与 Linux 上指纹相同；命令行输出不会因控制台编码而中断。详见 [更新日志](CHANGELOG.md)。

## 0.7.0 年度布局设计与复算

正式评分对每个可建设布局、每个工况重新求 APS，以代表小时累计吸收热量和热流不均匀惩罚。A/B 比较会列出镜数、边界、禁排区和镜距不符合要求的布局。结果页显示已找到方案的得分，并区分候选瞄准模型上的已证领先、并列和区间重叠。

`layout_opt.formal_position_trials` 控制按年度 APS 实算的自由镜位试探次数，`ranking_refine_states` 控制每个竞争布局追加求解的工况数，默认分别为 4 和 2。两个预算都可设为 0。运行记录支持从冻结的输入重算，命令行为 `cspaps replay-layout 运行目录 --out results`。外层算法基准和布局优化可通过 `scenarios.validation_file` 指定另一张复核工况表，复用相同的地图库。求解器基准只用联合姿态上界计算跨算法差距。

### 算法值得升级吗：同一条件下的证据（阿克塞，473 面镜）

- **功率**：四个工况的差都在 0.15% 以内。

  - 低太阳高度时解析模型低估 5%（标准误 0.2%），属于模型误差：低太阳时像散使光斑变形，HFLCAL 的圆高斯光斑近似在这里偏差最大；这时热流离上限很远。

  - 逼近限制时两者相差 0.1%，追迹确认峰值为上限的 0.884 ± 0.009，在 95% 的允许值以内。
- **噪声的影响**：每镜只用 300 条光线时，云影边缘的峰值差是 −11.5%，主要来自噪声图最大值的偏高；加密后为 −0.9%。
- **热点距离**：λ = 0.3 的方案热流很平，最热格可在几米外的平台上任意落点，所以热点距离 3.7–4.7 m 只说明两图的最大值不在同一格，不说明热点位置算错。
- **求解差距**：低太阳时的 24% 来自上界不计阴影遮挡，并不说明方案差。

**内层：四种瞄准方法**（界面「光学校验 → 求解器对比」）。取 h_s × DNI 最大的 6 个工况，候选集、网格与 5% 裕度相同，每种方法每个工况的预算为 60 s。差距相对每个工况所有方法中最小的有效上界。

| 方法 | 算例设置（λ = 0.3，限值 1000 kW/m² 不起作用）：平均 / 最大差距 · 平均用时 | 限值起作用（λ = 0，限值 388 kW/m²）：平均 / 最大差距 · 平均用时 |
| --- | --- | --- |
| 贪心 APS（现行） | 0.23% / 0.29% · 6.9 s | 0.004% / 0.025% · 2.6 s |
| 固定响应 0/1 规划（HiGHS） | 0.22% / 0.32% · 40.6 s（1 个工况超预算） | 同上 · 63.9 s（用满时限） |
| 子场分解（4 扇区，可并行） | 0.22% / 0.27% · 6.6 s（理想并行 6.5 s） | 同上 · 2.7 s |
| 贪心 + 松弛取整与对偶上界 | **0.06% / 0.07%** · 23.9 s，6 个工况都最好 | 同上 · 6.9 s |

全部 48 个方案都通过细网格复核。

- **松弛取整**：λ > 0 时把差距从 0.23% 降到 0.06%，用时约 3.5 倍。布局排名的价值区间重叠时值得打开（`layout_opt.inner_certify_rounds`）。
- **整数规划**：固定光斑响应的 0/1 规划不比贪心好，还慢 6–25 倍；它只最大化功率，均匀性要事后处理。
- **子场分解**：质量与贪心相同。473 面镜时扇区求解只占总时间的一小部分（响应计算与联合姿态复核占大头），所以并行收益不大，留作大镜场的选项。
- **限值起作用时**：四种方法给出同一方案，离上界不超过 0.025%。

**外层：两种布局搜索。** 同一场地、473 面镜、λ = 0.3，每次运行 300 s，种子 1、2。输出布局用正式 V(L) 在两组工况上评分：训练集是 12 个工况；留出集用种子 + 1000，有 17 个工况，代表太阳位置不同。

- 同样的时间预算下，参数化的差分进化在训练和留出工况上都明显领先，两个种子的结果几乎相同。
- 自由镜位法评估次数多约 20 倍，但只比初始镜场好 0.1–0.2%：单镜能量梯度把镜子推向塔，阴影遮挡和最小镜距又把它们挡回来。
- 两种方法在留出工况上的名次与训练工况一致，说明领先不是代表工况的偶然结果。

**结论**：

- 内层值得加松弛取整（约 3.5 倍时间）。默认不开，以免正式排名时间翻几倍；布局的价值区间重叠时，在「工况与地图的高级设置」里设 `inner_certify_rounds` 打开。
- 整数规划和子场分解在这个规模上没有收益。
- 外层保留差分进化。
- 解析模型的功率可直接用于排名。低太阳高度的峰值偏低约 5%，靠 5% 的安全裕度兜底；离上限近时应以细网格复核和光线追迹为准。

## 0.5.0 逐工况 APS 评价镜场的全年布局价值

按 [需求清单](docs/APS-LAYOUT-REQUIREMENTS.md) 全部实现并逐项验收，推导见 [模型说明 0.5 节](docs/MODEL.md)。

**怎样评价一套镜位。** 每个代表工况 s 给出太阳方向、代表小时数 h_s 和一张覆盖整个场地的 DNI 地图 D_s(x, y)（场地坐标，与布局无关）。镜子在哪里就读哪里的 DNI；每个参与排名的布局在每个工况下都重新求解问题一（内层权重 λ_APS，目标 P − λ_APS·U，U = A_H·σ_H 为考核区二维吸收热流的面积加权标准差乘面积，与问题一完全相同），再在**这组瞄准结果**上计分：

```
V(L) = Σ_s h_s (P_s − λ_L U_s) = E(L) − λ_L Π(L)          E = Σ_s h_s P_s（总吸热，单独报告），Π = Σ_s h_s U_s
```

- 内外层权重独立。两者相等时 V 就是各工况内层得分的加权和；只改 λ_L 时不重新求解，P_s、U_s 不变，V 沿斜率 −Π 的直线变化（界面拖动即重新排名）。
- 两套布局之差 ΔV = ΔE（更多吸热）+ (−λ_L ΔΠ)（更均匀受热）。先在每个工况考核热流不均匀，再按小时累加，不同时刻的热点不会在年平均热流图上相互抵消。
- 每个工况的状态与计分（可行运行计 h·(P − λ_L·U)；可行停机、无日照、未找到可行方案、已证不可行计 0；未求解则该布局不排名）写在结果表里。导出的逐工况表与逐镜瞄准方案可独立复算（`cspaps rescore`），`cspaps scenario-aps` 或界面「瞄准优化 → 年度工况复核」可独立复核任一工况，结果与布局工作区逐位一致。
- 中心瞄准只用于标注明确的快速初筛；初始镜场（最靠近塔的 N 面）一起排名作对照。外层上界在每个栅格取地图的 DNI 最大值，只对所用工况集成立。

**云影对比**（界面「云影对比与回放 → 单时刻云影对比」，`cspaps cloud-compare`）：云来之前的镜场 DNI、三维光束示意、各镜中心对应的瞄准点（标在吸热器展开图上）与热流；云来以后不改策略与重新 APS 的热流、总热量、均匀性（数值与图并列）；云突然散去仍执行云下方案的通量风险，以及按晴空 DNI 校核通量的防云散方案。

**结论**

1. **布局决定周向受热，三个站址一致。** 只追求能量时镜子挤向极侧（北半球塔北 95–100%，南半球的奥古斯塔港塔南 90%），管屏间 CV 0.9–1.3；λ_L = 0.3 时极侧占比降到 48–51%，CV 降到 0.11–0.28，代价是 4–15% 的理论能量。
2. **逐工况 APS 的正式排名可以逐项追溯，而且会改变结论。** 阿克塞、奥古斯塔港、哈密（均匀 DNI）的胜出布局比初始布局分别高 108、157、119 MWhₜₕ，优势来自更多吸热（ΔE +258 / +340 / +264），一部分被更不均匀的受热抵消（−150 / −183 / −145）。哈密的三个中心瞄准初筛布局在正式口径下都不如初始布局（−43 到 −78），只有按 V 接受的换位之后才反超——中心瞄准的初筛不能替代逐工况 APS 排名。
3. **代表工况误差小且不改变排序。** 20 个工况相对 40 个工况的 V 偏差为 +0.4% 到 +0.9%（持久性地图或均匀 DNI），各布局偏差相近，排序一致；10 张云图时为 +5%（每张云图只分到 2 个代表工况）。内层年度差距约 4%，最大单工况差距 15–26% 出现在太阳高度角 14–19° 的工况（上界放松了阴影遮挡，不是方案差）。
4. **空间 DNI 改变的主要是受热均匀性。** 持久性的半场亮暗或梯度使 Π 增加（阿克塞 +30%），V 下降约 1.4%；布局之间的领先幅度变化不大（阿克塞 +101 → +108，奥古斯塔港 +72 → +157）。
5. **瞬时云影不应决定镜位。** 哈密用云影地图做布局时，胜出布局只在自己的云图上领先初始布局（4 张云图 +4,861、10 张云图 +1,244 MWhₜₕ），换一组独立云图后落后（−844、−589），均匀 DNI 下也落后（−1,329）——优化器学会了躲开固定位置的云。在均匀 DNI 上设计的布局在两组独立云图上都稳定领先（+412、+269）。软件在云影模型下自动用独立云图复核胜出布局并在结果页提示（`layout_opt.cross_check_maps`）。镜位应按持久性的空间 DNI（或均匀 DNI）设计，云影地图用来检验运行与受热均匀性。
6. **云来时重新 APS 的价值在均匀性。** 两块云遮住 121 面镜：沿用晴空方案时吸收功率降约 20%，二维 CV 从约 0.24 升到 0.37–0.38；按云下 DNI 重新求解，功率基本不变而 CV 回到 0.25–0.34，目标 J 提高 0.33–0.59 MW。演示电站的吸热器不受通量限制（云散后执行云下方案的峰值为上限的 28–37%），所以防云散方案在这里不需要让步。

## 0.4.0 的两个设计工作区

**固定镜场瞄准。** 输入逐镜 XYZ、镜面尺寸、圆柱接收器及逐镜 DNI。选择功率最大、均匀性权重或 CV 上限。结果记录逐镜瞄准坐标、实际混合姿态下的吸收功率、考核区二维 CV 和热点。小规模问题枚举全部离散组合。较大问题通过松弛取整和联合姿态邻域搜索改进，并给出与所得方案对应的模型上界。允许散焦、最低负荷和设备通量限制均参与存在性判断。

**全年镜场布局。** 给定场界、镜数、镜面、接收器和站址气象。在最小镜距、边界与塔周禁排区内搜索布局。均匀性可选管屏之间或整个受热面的二维离散度。默认演示按中心瞄准的全年理论目标排名，标准预设对入围方案用实际逐时天气复算。切换到 APS 搜索时，按实际姿态的可行运行能量及其均匀性排名。每个结果注明瞄准策略、复核工况数、加权目标及其上界。

Windows 本地安装开发依赖后，双击仓库根目录的 `Start-CSP-APS.cmd`。命令行入口为 `cspaps gui`。模型边界、计算公式和证书范围见 [模型说明](docs/MODEL.md)。

### 0.3 历史阿克塞算例

本节保留旧版固定响应求解器的基准。旧表中的差距只对应当时的响应矩阵。0.4 结果页按联合姿态重算并使用独立上界。

阿克塞地区 2024 年 NASA POWER 逐时 DNI；镜场与吸热器为模拟设计输入（`cases/aksai_demo.yaml`）。

**问题一**：473 面 8×8 m 定日镜，吸热器 Ø7 × 8 m、中心高 100 m，2024-03-19 15:00，DNI 1136.7 W/m²。每一行都经过细网格完整光斑复核，差距相对可证上界。

| 均匀度权重 λ | 吸收功率 (MW) | 考核区二维 CV | 复核峰值 (kW/m²) | 最优性差距 |
| --- | --- | --- | --- | --- |
| 0（功率最大） | 24.188 | 1.101 | 561 | 0.00%（候选集上已证全局最优） |
| 0.05 | 24.001 | 0.528 | 242 | 0.00% |
| 0.1 | 23.721 | 0.370 | 200 | 0.02% |
| 0.2 | 23.415 | 0.280 | 194 | 0.06% |
| 0.3 | 23.272 | 0.259 | 195 | 0.10% |
| 0.5 | 22.283 | 0.161 | 162 | 0.43% |
| 1.0 | 21.148 | 0.089 | 147 | 1.17% |

- 只损失 0.8% 吸收功率（λ = 0.05），二维 CV 就从 1.10 降到 0.53；损失 3.8%（λ = 0.3）降到 0.26。
- 单时刻含证书的计算约 15–20 s（4 核）；7 个 λ 的权衡曲线约 1 分钟。
- 证书针对离散候选瞄准点（默认 21 个）。候选点加密分析（`cspaps aps-refine`）：3×7 → 5×13 → 9×25 个候选点时，本方案 21.462 → 21.562 → 21.595 MW，上界 21.487 → 21.587 → 21.611 MW，1.5° / 0.3 m 分辨率下差距 0.07%。
- 最终状态来自对最终瞄准点重新计算阴影遮挡后的细网格复核；只有通过复核的精确法最优解才标记“已证全局最优”。

**问题二**：N = 473，840 m × 780 m 矩形场地，塔周禁排半径 50 m，最小镜距 12.45 m。「标准」计算强度约 2–3 分钟。

圆柱外置式吸热器的每一侧只被朝向它的定日镜照射，APS 只能沿高度、在几度范围内移动瞄准点，**吸热器各朝向的受热由镜位决定**。只追求全年能量时，高纬度场址的镜子会挤在塔北侧，吸热器南侧几乎不受热，瞄准策略无法补救。所以布局目标加入周向均匀度惩罚：

```
max_X  Σ_t w_t [P_t(X) − λ_L · A_H · σ_circ,t(X)]      （与问题一的 P − λ·A_H·σ_H 同构）
```

σ_circ 是各管屏平均吸收热流的标准差（管屏间吸热平衡）。候选镜位按“加入当前布局后”的阴影遮挡定价，选择与定价交替迭代，避免把从不建造的候选的遮挡算进来而选出孤立远镜。

同一组生成参数下只改变 λ_L 的对比：

| 指标 | 只追求能量（λ_L = 0） | 演示默认 λ_L = 0.3 |
| --- | --- | --- |
| 塔北侧镜子占比 | 95% | 48% |
| 能量质心离塔 | 170 m | 13 m（集热器位于镜场中心） |
| 管屏间吸热 CV（逐工况、能量加权） | 1.07 | 0.12 |
| 脱离主镜场的镜子 | 0 | 0 |
| 全年理论吸收热量（中心瞄准，含阴影遮挡） | 35,826 MWhₜₕ | 33,709 MWhₜₕ（约 −6%） |
| 受限 APS 可行年吸收热量 | — | 32,167 MWhₜₕ |
| 任意布局、任意瞄准策略的年能量上界 / 差距 | 39,283 | 39,283 / ≤ 14.2%（多出的差距是均匀性的代价） |
| 候选集上镜位选择的差距（Frank–Wolfe 证书） | — | 0.04% |

两种布局在问题一中的表现（2024-03-19 15:00，DNI 1136.7 W/m²，细网格复核）：

| 问题一的权重 λ | 能量最优布局：吸收功率 / 二维 CV | λ_L = 0.3 布局：吸收功率 / 二维 CV |
| --- | --- | --- |
| 0 | 26.32 MW / 1.42 | 24.15 MW / 0.78 |
| 0.3 | 25.59 MW / 1.04 | 23.08 MW / 0.23 |
| 1.0 | 11.57 MW / 0.73 | 20.65 MW / 0.06 |

能量最优布局的周向 CV 在任何 λ 下都在 0.7 以上；环绕布局下瞄准策略能把二维 CV 降到 0.06，功率仍有 20.7 MW。界面「布局优化 → 能量–均匀度权衡」可以对任意 λ_L 序列画出这条曲线（每点数秒）。

上界忽略邻镜阴影遮挡并允许最密堆积，因此偏乐观；真实全局最优介于优化结果与上界之间。上界对栅格每个格子内的任意位置、任意瞄准点严格成立（不依赖格点取样），推导见 [docs/MODEL.md 第 0.2 节](docs/MODEL.md)。

## 安装

```bash
python -m venv .venv
```

```powershell
python -m venv .venv
```

| 云影对比与回放 | **单时刻云影对比**：① 云来之前的镜场 DNI、三维光束、各镜中心瞄准点（吸热器展开图）与热流；② 云来以后的 DNI 变化；③ 不改策略时的热流、总热量、均匀性；④ 重新 APS 的新瞄准点（标出移动）与热流；⑤ 云突然散去的通量风险与防云散方案；全部数值表与下载。**时序回放**：在线引擎逐周期决策，对比中心瞄准、仅当前 DNI、含预测三种策略。 |
| 光学校验 | 解析模型与光线追迹；**压力工况复核**（低太阳高度、云影边缘、高负荷混合瞄准、逼近热流限制，物理误差与求解差距分开列出，并导出逐镜 DNI 的 SolTrace 算例）；**求解器对比**（同一预算下的四种瞄准方法、两种布局搜索）；SolTrace 对标；遮挡筛选复核。 |
| 参数设置 / 运行记录 | 参数按设备和计算任务分组，常用选项附说明。每次计算保存独立参数快照、结果数据和图表，可回看或载入继续仿真。 |
| 方法与理论 | 两个问题的数学表述、存在性、上界推导和适用范围。 |

### 接入电站控制循环

**Python 接口**：

```python
from cspaps import load_case
from cspaps.field import build_field
from cspaps.engine import APSEngine, ControlRequest, ForecastSnapshot, Receipt

case = load_case("plant.yaml")
engine = APSEngine(case, build_field(case))
resp = engine.step(ControlRequest(
    time=now, dni=dni_per_heliostat, dni_time=t_meas,
    forecasts=[ForecastSnapshot(t, dni_t) for t, dni_t in forecast],
    available=in_service, receipt=Receipt(last.plan_id, last.aim_azimuth, last.aim_z, last.active)))
resp.state            # "ready" | "fallback" | "infeasible"
resp.to_frame()       # id, active, aim_azimuth_deg, aim_z, aim_x, aim_y, defocus_reason
```

**JSON 行服务**：`cspaps engine plant.yaml`。每行一个请求，DNI 可以用列表（按镜场顺序）或 `{"镜子ID": dni}`。场站的安全联锁独立于 APS，保持不变。
